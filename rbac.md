# Авторизация команд бота (RBAC)

Согласовано 24.09.2026, уточнено и реализовано 16.10.2026 (итерация 13, см. `PLAN.md`).
Цель: отдать бота в общее пользование, но команды про игроков и раздачу прав открывать только
своим, управляя правами из самого Telegram.

## Модель

**Ключ — `chat_id`, а не пользователь.** Так уже устроены `telegram_chats` и подписки:
минус в начале — группа, без минуса — личка. Выдал доступ группе — им пользуются все её участники;
это осознанное решение, а не побочный эффект.

**Исключение — раздача прав: она проверяется по человеку** (решение zalex 2026-10-16).
`/grant`, `/revoke`, `/roles` — всё, что требует `ROLE_ACCESS_MANAGE`, — страж проверяет по `from.id`
того, кто набрал команду, а не по чату. Личные права человека — это права его лички с ботом
(user_id равен её chat_id), второго хранилища нет. Поэтому root раздаёт права в любой группе ответом
на сообщение, а участники группы — нет, даже если группе выдали админа. Правило выводится из права
(`accessSubject` в `commandAccess.ts`), а не из списка команд. Человеком не считаются пост канала
(нет автора) и анонимный админ группы (`sender_chat`): из канала права не раздаются.

Ответ бота уходит в тот чат, где набрана команда: `/roles` в группе покажет назначения всем её
участникам.

**Состав ролей — в коде, назначение — в базе.** Повседневно меняется, *кому* выдана роль,
а не *что* она разрешает. Иерархия и карта «команда → право» живут в коде
(`src/access/Roles.ts`, `src/telegram/commandAccess.ts`), в базе — только «чату выдана роль».
Добавить роль или переложить команду — через выкат.

**Два вида ролей, одно пространство имён** (как в Symfony, всё — `ROLE_*`):

- **право** — одна команда вместе с её кнопками;
- **группа** — набор прав и других групп.

Выдать можно и группу, и отдельное право: так человеку даётся ровно одна возможность без новой
группы под неё. У чата может быть несколько ролей, права складываются.

Иерархия разворачивается транзитивно один раз при загрузке модуля в плоский набор на каждую роль:
проверка прав — вхождение в множество, без обхода дерева. Цикл в иерархии роняет старт.

## Схема

```
ROLE_ROOT ──┬── ROLE_PLAYER_USER ──┐
            └── ROLE_USER_ADMIN ───┴── ROLE_SERVER_USER        (+ ROLE_ANONYMOUS у всех)
```

| Группа | Право | Команды | Кнопки |
|---|---|---|---|
| **ANONYMOUS** — у всех, в БД не хранится | `ROLE_ANONYMOUS` | `/start`, `/help`, `/whoami`, `/message`, `/reply` | — |
| **ROLE_SERVER_USER** — по умолчанию, однократно при первом `/start` | `ROLE_SERVER_LIST` | `/serverlist` | `c:`, `m:` (листать, открыть карточку) |
| | `ROLE_SERVER_SUBSCRIBE` | `/my` | `k:` (карточка: подписка, проверка, галочки) |
| | `ROLE_SERVER_STATUS` | `/status`, `/time` | `s:r` |
| | `ROLE_SERVER_OBSERVED` | `/observed` | — |
| | `ROLE_TS_VIEW` | `/who` | — |
| **ROLE_PLAYER_USER** | `ROLE_PLAYER_WATCH` | `/watch`, `/wait`, `/unwatch` | `p:`, `pw:` |
| | `ROLE_PLAYER_LIST` | `/players` | — |
| | `ROLE_PLAYER_WHERE` | `/where` | `pc:` |
| | `ROLE_PLAYER_HISTORY` | `/history` | `ph:` |
| | `ROLE_PLAYER_ALIASES` | `/aliases` | — |
| | `ROLE_PLAYER_DOSSIER` | `/playerinfo`, `/steaminfo` | `pi:` |
| **ROLE_USER_ADMIN** | `ROLE_ACCESS_MANAGE` | `/grant`, `/revoke`, `/roles` | — |
| **ROLE_SERVER_ADMIN** (итерация 14) | `ROLE_SERVER_ADMIN_VIEW` — по чату | `/server <id>`; `/serverlist` показывает все серверы с `#id` | `a:o`, `a:k` (открыть, проверить) |
| | `ROLE_SERVER_MANAGE` — по человеку | `/server_add`, `/server_edit`, `/server_delete`, `/source_add`, `/source_edit`, `/source_delete` | `a:e`, `a:d`, `a:x`, `a:y`, `a:se`, `a:sd`, `a:sx` (вкл/выкл, удаление) |
| **ROLE_ROOT** — из `TELEGRAM_ROOT_CHAT_IDS`, отнять нельзя | всё | | |

`ROLE_SUPER_USER` из первой редакции переименован в `ROLE_PLAYER_USER`: «супер» читалось как
«почти root». `ROLE_SERVER_ADMIN` заведён в итерации 14 вместе с командами управления серверами;
root получает его через иерархию.

**Правило «видеть — по чату, менять — по человеку».** Просмотр зависит от аудитории: список уходит
в чат, его читают все. Правка — от того, кто её делает. По человеку проверяются `ROLE_ACCESS_MANAGE`
и `ROLE_SERVER_MANAGE` — и командами, и кнопками.

## Единая точка входа

Все наборы команд регистрируются на `Composer`, перед которым стоит **один** страж
(`telegram/AccessGuard.ts`); `TelegramBot` без стража не собирается — это обязательный параметр
конструктора. Один, а не по стражу на набор: в grammy middleware, не вызвавший `next()`, останавливает
апдейт целиком, и страж первого набора перекрыл бы команды всех следующих (так было в примере первой
редакции этого файла — ошибка).

**Fail closed по всем осям.** Дальше стража проходит только то, что есть в карте и разрешено:

- команда вне карты — молча отбрасывается (в группе ответ на каждую чужую команду засорял бы чат);
- запрещённая команда — ответ «нет доступа, /start или /whoami»;
- кнопка вне карты — «кнопка устарела» (общий перехватчик в `SubscriptionCommands` удалён: его роль
  взял страж); запрещённая — «⛔ Недоступно». Нажатие подтверждается всегда, иначе висит индикатор;
- обычный текст, правки сообщений, команды другому боту (`/cmd@OtherBot`) и прочие апдейты
  до обработчиков не доходят.

**Карта исчерпывающая, и это проверяет тест** (`commandAccess.test.ts`): настоящие наборы
регистрируются на записывающий `Composer`, и тест падает, если зарегистрированная команда или кнопка
не описана в карте, если в карте есть лишнее, если набор повесил обработчик мимо
`command`/`callbackQuery` (`on`, `use`, `hears`…), если у пункта меню нет права и если какое-то
право не открывает ни одной команды.

## Хранение

Миграция 009: `telegram_chat_roles`

| колонка | смысл |
|---|---|
| `chat_id` | → `telegram_chats`, знаковый bigint, `ON DELETE CASCADE` |
| `role` | строка `ROLE_*`; проверка значения в коде, не enum — иначе роль требовала бы миграции |
| `granted_by` | user_id выдавшего; `NULL` — роль по умолчанию или перенос миграцией |
| `granted_at` | когда |
| `note` | заметка для человека |

Первичный ключ — (`chat_id`, `role`). Роль из базы, которой нет в коде, игнорируется (warn в лог).

Плюс `telegram_chats.default_role_granted_at` — пометка однократной выдачи роли по умолчанию.

**Чаты, бывшие до прав, ничего не теряют:** миграция выдаёт им `ROLE_SERVER_USER` и ставит пометку.
Команд про игроков они при этом не получают — их раздаёт root.

**Root — из `TELEGRAM_ROOT_CHAT_IDS`** (через запятую) и в базе не хранится. Неудачным `/revoke`
себя не запереть. Опечатка в переменной роняет старт.

Роли кэшируются в памяти `AccessControl`; кэш чата сбрасывается при выдаче и отзыве.

## Как раздаются права

```
1. Деплой с TELEGRAM_ROOT_CHAT_IDS=<ваш user_id>       → вы root (id — из /whoami в личке)
2. Вася: /start                                        → ROLE_SERVER_USER автоматически
3. Вася: /whoami → «chat_id: 555»                       → присылает вам
4. Вы: /grant 555 player_user Вася из клана             → Вася видит команды про игроков
5. Вы: /revoke 555 player_user                          → снова только серверы, подписки на игроков удалены
```

| Где `/grant <роль>` | Кому |
|---|---|
| `/grant <chat_id> <роль> [заметка]` | чату с этим id |
| в группе **ответом** на сообщение человека | ему лично (его user_id = chat_id его лички) |
| в группе без ответа | всей группе |
| в личке без id | подсказка: адресат непонятен |

Роль пишется как удобно: `player_user`, `ROLE_PLAYER_USER`. Выдать можно только чату, который
боту уже писал (иначе — «пусть нажмёт /start»). Права выдающего проверяются **по нему лично**,
где бы он ни набрал команду; в `granted_by` пишется его user_id.

**Кто что может выдать** (`manageRefusal` в `Roles.ts`; одно правило на выдачу и отзыв —
отобрать можно ровно то, что ты мог бы выдать):

- `ROLE_ROOT` — никто и никогда, только env;
- нужно право `ROLE_ACCESS_MANAGE`;
- роль, дающая `ROLE_ACCESS_MANAGE`, — только root (иначе админы плодили бы админов);
- выдать можно только то, что есть у тебя самого.

**`/roles`** — обзор: root из конфига, сколько чатов на роли по умолчанию (числом: она есть почти
у всех, список рос бы с каждым `/start`), остальные назначения поимённо и справочник ролей, собранный
из тех же таблиц, что проверяет страж.

**`/roles <chat_id>`** или `/roles` ответом на сообщение человека — один чат: каждая роль с тем, кто
выдал, когда и с какой заметкой (роль по умолчанию так и подписана), root из конфига, назначения
с ролью, которой в коде больше нет («нет в коде, не действует»), и итоговый список доступных команд.
id группы даёт `/whoami`, набранная в ней. В группе `/roles` без ответа — обзор, а не роли группы.

**`/whoami`** — свой chat_id (в группе и user_id) и свои роли; доступна всем.

**Роль по умолчанию в миграции.** 009 вписала `'ROLE_SERVER_USER'` строкой — это запись однократного
события, а не ссылка на текущее умолчание. На чистой базе она ничего не вставляет и не падает.
Смена `DEFAULT_ROLE` в коде на неё не влияет: старые чаты сохранят `ROLE_SERVER_USER`, пока группа
с таким именем есть в коде. Переименование группы потребует миграции `UPDATE telegram_chat_roles`.

## Роль по умолчанию — однократно

Выдаётся при `/start` **один раз за всю историю чата**: иначе тот, у кого роль отобрали,
вернул бы её повторным `/start`. Пометка ставится условным `UPDATE … WHERE default_role_granted_at
IS NULL` — кто её поставил, тот и выдаёт; два одновременных `/start` роль дважды не выдадут.

## Отзыв забирает подписки

Потерянные права считаются по итогу (до отзыва минус после): право, оставшееся от другой роли,
потерянным не считается. Дальше решает composition root:

- потерян `ROLE_PLAYER_WATCH` → удаляются подписки на игроков и ожидания ников этого чата;
- потерян `ROLE_SERVER_SUBSCRIBE` → удаляются подписки на серверы, список опроса пересобирается.

Осторожно с чатом из `TELEGRAM_CHANNEL_ID`: его подписки — это табло TeamSpeak. Отзыв у него
`ROLE_SERVER_USER` опустошит табло.

## Что бот показывает

`/start`, `/help` и меню Telegram собираются **по правам чата**. Общее меню (область по умолчанию) —
это меню роли по умолчанию: её получает каждый при `/start`. Чатам, чьи права от неё отличаются,
публикуется персональное меню (`setMyCommands` со `scope: chat`) — при выдаче, отзыве и на старте
процесса; вернулись права к умолчанию — персональное меню снимается.

## Что не сделано

- Существующие подписки на игроков у чатов без `ROLE_PLAYER_WATCH` миграция **не трогает**:
  они продолжат получать уведомления, пока root не выдаст роль или не снимет подписки. Посмотреть:
  `SELECT DISTINCT chat_id FROM player_subscriptions;`
- Обычные команды проверяются у чата: личные права Васи на игроков в группе без прав не действуют.
  Для раздачи прав это не так, см. «Модель».
