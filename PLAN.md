### Тема: периодическая проверка актуального состояния — постановка (сделано в 8a)

**Проблема — одна причина, два симптома.** И TeamSpeak, и Telegram получают обновление только
в момент **изменения** состояния. Если именно эта доставка упала, повторять её некому.

- *TeamSpeak.* Все серверы легли → событие → TeamSpeak в этот момент недоступен → запись упала →
  состояние больше не меняется → в описании канала навсегда висит «online 12/64».
  Воспроизведено тестом в 5b (`доставлено: []`).
- *Telegram.* `serverOnline` эмитится только в момент **перехода** статуса. Если отправка упала,
  диспетчер запишет warning — и всё. Следующего `serverOnline` для этого сервера не будет, пока он
  не упадёт и не поднимется снова. Сообщение «сервер онлайн» потеряно окончательно.

**Ключевое различие, которое нельзя проигнорировать.** Описание канала TeamSpeak — это
**состояние** («сейчас 12/64»), переписать его повторно безвредно. Канал Telegram — это **журнал**,
сообщение в момент времени. Наивная «периодическая отправка текущего состояния» в Telegram даст
1440 сообщений «is online» в сутки и сделает канал непригодным.

**Идея, закрывающая оба случая.** Каждый канал запоминает, **что он успешно доставил**.
Периодическая проверка сравнивает это с текущим состоянием и отправляет только при расхождении:

```
12:00  сервер поднялся → отправка "is online" → УПАЛА
       последнее доставленное для этого сервера: "offline" (или ничего)
12:01  проверка: доставлено "offline", сейчас online → расхождение → отправляем → успех → запомнили
12:02  проверка: доставлено "online", сейчас online → совпадает → молчим
```

Одно сообщение с опозданием на минуту вместо потерянного навсегда, и никакого спама.
Для TeamSpeak то же самое, но «состояние» — это весь вид.

**Это лучше того, что предлагалось изначально.** Первым вариантом была безусловная перезапись
описания раз в минуту. Здесь запись происходит только когда она действительно нужна.

**Ложится расширением, без переписывания.**
- новая обёртка рядом с `LatestOnlyNotifier`: помнит ключ последней успешной доставки, пропускает
  событие с тем же ключом. Функция ключа задаётся при сборке — для TeamSpeak это весь вид,
  для Telegram «сервер + его статус»;
- периодический тик: спрашивает у монитора текущее состояние и прогоняет его через диспетчер
  обычными событиями.

Ни диспетчер, ни `TelegramStatusNotifier`, ни `TeamSpeakChannelNotifier` не переписываются —
они просто оказываются обёрнуты. Тот же приём, что сработал в 5b.

### Ответы на открытые вопросы (получены 2026-07-31, решения zalex)

**1. Ручная правка описания канала в TeamSpeak — должна откатываться.** Поэтому **для TeamSpeak
безусловная перезапись каждый тик, для Telegram сравнение с последним доставленным.** Механика
с обёртками это позволяет: разные обёртки на разные каналы. Цена — один лишний `channelEdit`
в минуту, даже когда ничего не изменилось; она признана приемлемой, потому что взамен само лечится
и упавшая доставка, и правка руками.

**2. Статус `unknown` — уведомления не нужны.** У сервера три состояния (`online`, `offline`,
`unknown` — сразу после старта, пока не было ни одного ответа), а событий два. Сервер в `unknown`
периодическая синхронизация в Telegram **пропускает**. В описании канала TeamSpeak он при этом
отображается как есть: `unknown` — часть вида.

**3. Период — 60 000 мс, переменная `MONITOR_STATE_SYNC_INTERVAL_MS.`** Имя в семье существующих
`MONITOR_POLL_INTERVAL_MS` / `MONITOR_SUSPICIOUS_POLL_INTERVAL_MS`.

### Где размещает таймер (сделано)

## Принципы работы

1. **Итерациями.** Одна итерация = одна проблема = один осмысленный коммит. Не смешиваем.
2. **Каждая итерация описана по четырём пунктам:** какую проблему решаем → в чём проблема состоит
   сейчас (с файлами и строками) → как решаем → к какому проверяемому результату это приводит.
3. **Понимание важнее скорости.** Ни один шаг не делается «на доверии». Если непонятно зачем —
   останавливаемся и разбираем, а не идём дальше.
4. **Результат должен быть проверяемым.** Не «стало чище», а «`grep` не находит X» / «тест падал, теперь
   зелёный» / «приложение стартует с таким `.env`».
5. **Поведение и структура не меняются в одном шаге.** Либо переносим код без изменения логики, либо
   меняем логику, не перекладывая файлы.

Приведены к одной схеме имена реализаций каналов доставки. Логика: **имя несёт место доставки,
событие добавляется только когда для одного места их несколько.** Событие и так явно указано

| из | в |
|---|---|
| `TSNotifier` | `TeamSpeakChannelNotifier` |
| `TelegramOnlineHandler` | `TelegramOnlineNotifier` |
| `TelegramOfflineHandler` | `TelegramOfflineNotifier` |
| `NotificationHandler` (интерфейс) | `Notifier` |
| `NotificationSubscription.handler` | `.notifier` |

| `LogNotifier` | без изменений |

Заодно убраны два дангling-идентификатора в `properties.ts`, названных по классу, которого больше

`teamSpeakChannelsConfig`, экспорт `tsNotifierChannelNames` → `teamSpeakChannelNames`.

в `.env` и в прод-конфигурации.

Почему `Notifier`, а не `Handler`: «handler» говорит только «что-то обрабатывает», не отвечая
на вопрос что именно и зачем. `Notifier` отражает бизнес-функцию — класс уведомляет. Слово
`handlers` в структуру папок не введено по той же причине.

**Отвергнутые варианты.** По действию (`ChannelDescriptionUpdater`, `StatusLogWriter`,
`ServerOnlineAnnouncer`) — три разных слова для одной роли, по именам не видно, что классы одного
вида и взаимозаменяемы. По схеме «событие → место» (`ServerOnlineToTelegram`) — самодокументируемо,
но дублирует событие из списка подписок, имена длинные, и схема рассыпается, если класс подпишется
на два события.

Правило записано в `AGENTS.md`, §10.

### Итерация 0 — Остановить кровотечение

Не архитектура. Три независимых бага, которые уже живут в проде.

**Проблема.** Есть отказы, которые происходят молча: сервер перестаёт опрашиваться, и никто не узнаёт.

**Как сейчас.**
- `ProbeScheduler.ts:85` — `await task.run()` без `try/catch`. Любое исключение внутри (включая
  обработчики событий, которые выполняются синхронно на `emit`) не даёт дойти до строки 89
  с перепланированием. Таймер для этой задачи не создаётся заново **никогда**. Один сервер тихо
  выпадает из мониторинга до рестарта процесса.

### Итерация 5 — Политика уведомлений как доменное понятие

**Проблема.** Нет места, куда положить правило «что, куда и когда отправлять». Именно это блокирует

- маршрутизация выполняется дважды — `NotificationDispatcher` раздаёт по `event.type`, и каждый нотифаер начинается
  с `if (event.type !== "...") return`, то есть с проверки, которая не может сработать;
- две событийные номенклатуры (события `ServerMonitor` и union `NotificationEvent`) и ручной адаптер

- `emit`/`on` со строковыми именами не проверяются компилятором: опечатка = тихий no-op;
- `ServerProbe` эмитит `playersChanged` и `serverStatusChanged` в пустоту;

**Что делаем.** Одна типизированная событийная номенклатура вместо двух. Убираем двойную
маршрутизацию. Мёртвым событиям — либо подписчик, либо удаление. Coalescing для обновления описания
канала: устаревшие обновления отбрасываются, а не выстраиваются в очередь. И главное — заводим явное
место для политики: шаблоны текста, rate limit, тихие часы.

**Результат.** Добавление нового канала доставки (LLM-текст, озвучка через SinusBot) = один новый

«молчать ночью» реализуется в одном месте, а не в трёх нотифаерах.

**Почему здесь.** Опирается на итерации 2 (единая композиция), 3 (доменные типы) и 4 (границы слоёв).

**Проблема.** Событийная система не проверялась компилятором, из-за этого в нотифаерах жили защитные
проверки, а в `ServerProbe` — события без подписчиков.

**Как было.**
1. Маршрутизация выполнялась дважды: диспетчер роутил по `event.type`, и каждый нотифаер начинался
   с `if (event.type !== "...") return`. Убрать проверку было нельзя: `notify` принимал весь union,
   и без сужения `event.snapshot` не компилировался.
2. Неверную подписку компилятор пропускал: `{event: "serverOnline", notifier: new LogNotifier(log)}`
   собиралось, а в рантайме нотифаер получал чужое событие и молча выходил по guard'у.
3. `emit`/`on` со строковыми именами не проверялись вообще.
4. `playersChanged` и `serverStatusChanged` эмитились без подписчиков. Ради второго собирался объект
   `ServerStatusEvent`, из которого тут же брали одно поле, — с авторским комментарием
   «Тут пока несрастуха».

**Что сделали.**
- `notifications/events.ts` — `NotificationEventOf<TType>` (сужение union по типу) и
  `Notifier<TType>`: `notify` принимает уже суженное событие. Появилась функция
  `subscribe(event, name, notifier)`, которая связывает тип события с типом нотифаера.
  **Приведение типа осталось ровно одно — внутри `subscribe`,** и оно безопасно по построению:
  диспетчер вызывает подписку только для события её типа. Взамен на N рантайм-проверок получили
  одну документированную границу.
- Все четыре нотифаера потеряли `if (event.type !== ...)`. `TelegramOnlineNotifier implements
  Notifier<"serverOnline">` — и `event.snapshot` доступен без сужения.
- `main.ts` — подписки собираются через `subscribe(...)`, стало короче и читается как таблица.
- `monitoring/ServerMonitor.ts`, `monitoring/ServerProbe.ts` — типизированные карты событий
  через `EventEmitter<T>` (`ServerMonitorEvents`, `ServerProbeEvents`). Словари намеренно
  **разные**: монитор не должен знать, что его события кто-то доставляет; перевод в
  `NotificationEvent` остаётся в composition root.
- `playersChanged`, `serverStatusChanged` и `ServerStatusEvent` удалены. У probe осталось два
  события — переходы статуса. Заодно упростились `commitChanges` и `emitStatusEvents`: параметр
  `previousInfo` стал не нужен.

**Результат — проверено.**
- Ни одного `if (event.type !==` в проекте.
- **Неверная подписка не компилируется.** Проверено отдельным пробным файлом:
  `subscribe("serverOnline", "log", new LogNotifier(log))` → `TS2345: Argument of type 'LogNotifier'

### Итерация 5a-2 — Слияние Telegram-нотифаеров

Довеска к 5a: возникла из вопроса «а если один нотифаер должен обслуживать много событий — я что,
буду плодить сто классов?».

**Ответ на вопрос (проверено компилятором).** `Notifier<TType>` принимает **объединение** событий
любой ширины, поэтому один класс на событие никогда не требовался:
- `Notifier<"serverOnline">` — одно событие;
- `Notifier<"serverOnline" | "serverOffline">` — два;
- `Notifier<NotificationEventType>` — все, то есть в точности прежнее поведение.

Строгость при этом сохраняется: несовпадение объявленных событий с типом подписки по-прежнему
TS2345. Проверено пробным файлом со всеми тремя случаями.

**Проблема.** Два класса отличались одним словом в тексте (`is online` / `is offline`). Расширение
шло по классам вместо строк данных: пятьдесят вариантов текста означали бы пятьдесят классов.

**Что сделали.**
- `notifications/TelegramStatusNotifier.ts` — один нотифаер на `"serverOnline" | "serverOffline"`.
  Текст берётся из `STATUS_TEXT: Record<ServerStatusEventType, string>`. `Record`, а не `switch`
  и не `Map`: компилятор требует запись для каждого события объединения, поэтому забыть текст нельзя.
- Появился интерфейс `MessageSender { send(text): Promise<void> }`, объявленный у потребителя —
  как `ChannelDescriptionEditor` у TeamSpeak-нотифаера. До этого Telegram-нотифаеры зависели
  от **конкретного** класса `TelegramSender`, который тянет grammy; из-за этого у них не было
  ни одного теста. Теперь зависимость узкая, и тесты появились.
- `main.ts` — один экземпляр регистрируется на оба события:
  `subscribe("serverOnline", ..., telegramStatus)` и `subscribe("serverOffline", ..., telegramStatus)`.
- `TelegramOnlineNotifier.ts` и `TelegramOfflineNotifier.ts` удалены.

**Результат — проверено.**
- Тестов 50 (было 45). Пять новых на `TelegramStatusNotifier`: текст на `serverOnline`, текст
  на `serverOffline`, один экземпляр обслуживает оба события, имя берётся из снапшота, отказ
  транспорта пробрасывается наружу для логирования диспетчером.
- **Exhaustiveness таблицы проверена ломанием:** добавил `"statusViewChanged"` в объединение
  без текста → две осмысленные ошибки. `TS2741: Property 'statusViewChanged' is missing in type
  ... but required in type 'Record<ServerStatusEventType, string>'` и `TS2339: Property 'snapshot'
  does not exist on type '{ type: "statusViewChanged"; ... }'`. То есть компилятор поймал и
  отсутствующий текст, и то, что у этого события нет нужных нотифаеру данных.
- `tsc` чисто, приложение стартует.

**Правило записано в `AGENTS.md`, §10:** разные транспорты → разные классы; один транспорт, разная
логика доставки → разные классы; один транспорт, отличается только текст или данные → один класс
плюс `Record`-таблица.

**Что дальше по этой линии.** Когда понадобятся разные шаблоны и разметка, таблица уедет
за рендерер: он будет собирать текст, а нотифаер останется только доставкой. TODO с этим стоит
в коде. Это и станет содержанием шага 5c, но уже под конкретную задачу, а не под догадку.

**Статус:** ✅ сделано 2026-07-30. Закоммичено `00b13df`.

### Итерация 5b — Склейка обновлений TeamSpeak

**Проблема.** Обновления описания канала копились в неограниченной очереди, хотя осмысленно только
последнее.

**Как было.** `emitChangedIfNeeded()` вызывается после опроса **каждого** сервера, поэтому при четырёх
серверах за цикл могло уйти до четырёх `viewChanged`. Каждое шло через `void dispatcher.notify(...)`,
то есть без ожидания: вызовы не выстраивались по одному, а все уходили в `channelEdit` на единственное
SSH-соединение, где библиотека выполняет их последовательно. Если TeamSpeak отвечает медленнее,
чем приходят события, очередь растёт неограниченно. При этом первые обновления к моменту отправки
уже устарели: для табло состояния имеет смысл только последнее.

**Что сделали.** `notifications/LatestOnlyNotifier.ts` — обёртка над любым нотифаером:
- каждое событие перезаписывает «отложенное», промежуточные выбрасываются;
- если доставка уже идёт, вызов возвращается сразу — текущий цикл сам подхватит свежее событие;
- цикл крутится, пока отложенное не опустеет, поэтому в очереди никогда не больше одного;
- `finally` сбрасывает флаг доставки, чтобы упавшая доставка не залипала навсегда.

**Почему обёртка, а не логика внутри `TeamSpeakChannelNotifier`.** У того своя работа — отрендерить
и записать описание. Решение «промежуточные не нужны» — это политика доставки, и она должна быть
видна в `main.ts`, а не спрятана внутри класса. Плюс Telegram оборачивать **нельзя**: там каждое
событие самостоятельный факт, который нельзя потерять, — и в composition root это различие теперь
читается явно.

**Результат — проверено.**
- 5 новых тестов на управляемом нотифаере (доставку можно задержать и отпустить вручную, без
  таймеров и гонок): одиночное событие; **из четырёх наложившихся доставляются 10 и 13, а 11 и 12
  выброшены**; события без наложения доставляются все; отказ пробрасывается наружу для логирования
  диспетчером; после отказа обёртка не залипает.
- Тест ловит регрессию: убрал ранний `return` при идущей доставке — падает именно тест про склейку.
- Тестов 55 (было 50), `tsc` чисто, приложение стартует.

**Ошибка в моём первом варианте теста.** Я ждал промис первого вызова до того, как отпустил вторую
доставку, — получился дедлок («Promise resolution is still pending but the event loop has already
resolved»), и он повалил остальные тесты файла каскадом. Причина в семантике обёртки: промис вызова,
который **владеет циклом доставки**, разрешается только когда цикл опустеет полностью, то есть после
доставки чужих событий тоже. Семантику оставил такой: у любого отказа всегда есть вызывающий,
которому его можно пробросить. Альтернатива (разрешать промис после своей доставки, остальное —
в фоне) оставила бы фоновые ошибки без получателя.

**Найдена дырка в этом же шаге — по разбору с zalex.** Вопрос был: «не может ли сообщение зависнуть,
когда `pending` уже проставлен, а `delivering` ещё `true`?»

- **В успешном пути — нет.** Между последней проверкой `while (this.pending !== undefined)` и
  `delivering = false` в `finally` **нет ни одного `await`**: выход из цикла, из `try` и выполнение
  `finally` синхронны, а JS однопоточен — вклиниться туда нечему.
- **В пути с ошибкой — да, дырка есть.** Проверено экспериментом: доставка падает, цикл выходит,
  и накопленное состояние остаётся в `pending`, но забрать его некому. Прогон показал
  `доставлено: []`.

Почему это хуже, чем кажется: `ServerMonitor` эмитит `viewChanged` только при **изменении**
состояния (сравнение с `lastViewKey`). Значит если состояние больше не меняется — а это ровно случай
«все серверы легли и лежат» — следующего события не будет, и в описании канала навсегда останется
устаревшее «online 12/64».

Мой комментарий в коде описывал это неверно: я написал «упавшее событие теряется, его заменит
следующее», а теряется **ожидающее**, и заменить его может быть нечему. Комментарий исправлен.

**Что сделали по этому поводу (вариант 1 из трёх, выбор zalex).** `LatestOnlyNotifier` получил
`Logger` и пишет warning `Pending notification dropped after delivery failure`, когда выбрасывает
накопленное состояние из-за отказа. Дырка не лечится, но перестала быть молчаливой; поведение
зафиксировано отдельным характеризационным тестом.

**Отклонённые варианты.** Повтор с backoff внутри обёртки — закрывает только короткий сбой TeamSpeak,
но не главный сценарий (состояние больше не меняется), и утраивает размер обёртки.
Периодическое подтверждение состояния — правильное лечение, но это отдельный шаг: меняет модель
с «доставляем события» на «синхронизируем состояние», требует решить период и добавить таймер.
Договорились зайти в него отдельно. Записано в долг как п. 24.

**Что НЕ закрыто.** Лишняя работа из п. 12 долга осталась: вид по-прежнему пересчитывается
и сериализуется N раз за цикл. Закрыто только её последствие — очередь `channelEdit`.
Плюс п. 24 — см. выше.

**Статус:** ✅ сделано 2026-07-30, закоммичено `5ee6d83`. Тестов 56.

### Итерация 8a — Периодическая синхронизация состояния: TeamSpeak

Номер следующий свободный: 6 («мигратор») и 7 («операционная зрелость») остаются запланированными,
номер отражает порядок появления, а не выполнения. Разбита на 8a (вид → TeamSpeak) и 8b (статусы →
Telegram): шаги независимы, и 8b без 8a не нужен.

**Проблема.** Упавшую доставку никто не повторяет.

**Как было.** `LatestOnlyNotifier.ts:45-60` — доставка упала, цикл вышел, накопленное состояние
выброшено с warning'ом. `ServerMonitor.ts:129-138` эмитит `viewChanged` только при **изменении**
вида, поэтому если состояние больше не меняется (ровно случай «все серверы легли и лежат»),
следующего события не будет и описание канала останется врущим навсегда. Воспроизведено тестом
в 5b: `доставлено: []`.

**Что сделали.**
- `notifications/StateSync.ts` (новый) — публикует текущее состояние по запросу. Зависит от двух
  узких интерфейсов, объявленных здесь же: `CurrentStateSource { getView() }` и
  `StatePublisher { notify(event) }` — тот же приём, что `ChannelDescriptionEditor` у TeamSpeak-нотифаера
  и `MessageSender` у Telegram-нотифаера. **Часов внутри нет:** когда тикать, решает `Scheduler`
  в composition root, поэтому класс тестируется без таймеров.
- `notifications/events.ts` — новое событие `statusViewRefreshed` с теми же данными, что
  `statusViewChanged`.
- `notifications/TeamSpeakChannelNotifier.ts` — `Notifier<"statusViewChanged" | "statusViewRefreshed">`.
  Различать события внутри нечего: работа одна — отрендерить и записать. Приём из 5a-2: один класс
  на несколько событий.
- `monitoring/ServerMonitor.ts` — публичный `getView()`; `emitChangedIfNeeded()` тоже переведён
  на него, поэтому вид собирается в одном месте.
- `properties.ts` — `stateSyncProperties.intervalMs`, env `MONITOR_STATE_SYNC_INTERVAL_MS`,
  default 60 000. Отдельным convict-блоком, а не полем в `MonitorProperties`: монитор про эту
  периодику не знает, и давать ему конфиг, который он не читает, — вранье в сигнатуре.
- `main.ts` — второй `Scheduler` с единственной задачей `stateSync`; TeamSpeak-нотифаер подписан
  на оба события **одним экземпляром** обёртки (иначе периодическая синхронизация и реальное
  изменение получили бы по своей очереди доставки, то есть склейка сломалась бы); `stop()`
  добавлен в shutdown.

**Почему отдельный тип события, а не `statusViewChanged`.** `LogNotifier.ts:9` пишет вид в лог
на уровне **info**. При переиспользовании получили бы info-строку с полным видом каждую минуту,
а текст «Событие statusViewChanged» стал бы неправдой, когда ничего не менялось. Это то же
возражение, из-за которого мы отвергли таймер внутри `ServerMonitor`. Ценой одного варианта в union
подписчик теперь выбирает: табло берёт оба события, журнал — только изменения.

**Почему первый тик уходит сразу.** `Scheduler.start()` планирует задачи с нулевой задержкой.
Следствие: сразу после рестарта в описание уедет вид со статусами `unknown`, и через один
`MONITOR_POLL_INTERVAL_MS` (5 с) он заменится настоящим. Оставлено так осознанно: взамен сломанное
руками описание лечится сразу после рестарта, а не ждёт первого изменения состояния.

**Результат — проверено.**
- `npx tsc -p tsconfig.json --noEmit` — чисто. Тестов 61 (было 56), три прогона без флака.
- Ключевой тест — **тот самый сценарий 5b целиком, через настоящий `NotificationDispatcher`**:
  доставка падает, накопленное состояние теряется (`доставлено: []`), затем тик доставляет
  актуальное. Ещё четыре: вид публикуется событием `statusViewRefreshed`; каждый тик берёт
  состояние заново, а не запомненное при сборке; три тика при неизменном состоянии дают три записи
  (так откатывается правка руками); лог **не** получает переопубликованное состояние, но

пересчитывается N раз за цикл) тоже остался: периодический тик делает мгновенную реакцию
на изменение необязательной, но убирать её — отдельное решение, оно ухудшит время реакции
с «сразу» до «до минуты».

**Статус:** ✅ сделано 2026-07-31. Тестов 61.

### Итерация 8b — Периодическая синхронизация состояния: Telegram

**Проблема.** Упавшая отправка в Telegram терялась окончательно.

**Как было.** `serverOnline` рождается только на переходе статуса (`ServerMonitor.ts:127-133`).
Если отправка упала, диспетчер записал warning — и всё; следующего события для этого сервера
не будет, пока он не упадёт и не поднимется заново. Тем же лекарством, что в 8a, это не лечится:
канал Telegram — журнал, а не табло, и безусловная периодическая отправка дала бы 1440 сообщений
«is online» в сутки.

**Что сделали.**
- `notifications/ChangesOnlyNotifier.ts` (новый) — обёртка «только при расхождении». Помнит
  по каждому предмету последнее **успешно доставленное** состояние и молчит, если оно совпадает.
  Что считать предметом и состоянием — задаётся при сборке: для Telegram это «сервер» и «его статус»,
  поэтому падение одного сервера не глушит сообщение про другой.
- `notifications/StateSync.ts` — тик публикует ещё и статусы серверов по снапшоту монитора. Какое
  событие какому статусу соответствует, задаёт таблица `Record<ServerStatus, ...>`: `online` →
  `serverOnline`, `offline` → `serverOffline`, `unknown` → `undefined`, то есть **не публикуем**
  (решение zalex). `Record` заставит компилятор потребовать решение, если статусов станет больше.
- `main.ts` — Telegram-нотифаер обёрнут, TeamSpeak не обёрнут (у него безусловная запись). Ключи
  заданы здесь же двумя лямбдами: `event => String(event.snapshot.config.id)` и `event => event.type`.

**Почему запоминаем ДО отправки, а при отказе откатываем.** Наивный порядок «отправить, потом
запомнить» ломается на одновременных вызовах: тик и реальный переход статуса приходят независимо
(через `void`), поэтому оба успели бы пройти проверку до записи — и в канал ушло бы два одинаковых
сообщения, ровно тот спам, от которого обёртка защищает. Откат сделан аккуратным: если за время
отправки по этому же серверу доставили **другое** состояние, затирать его нельзя, поэтому
удаляем только своё (`if (delivered.get(subject) === state)`).

**Ловушка сборки, которая нашлась при написании тестов.** Обёртка обязана быть **одним экземпляром
на оба события**. Двумя разными память разъезжается: обёртка «online» продолжала бы считать, что
online уже доставлен, хотя между ними был offline, — и повторный подъём сервера остался бы без
сообщения. Сначала я сам так и написал тест (по обёртке на событие), заметил расхождение с `main.ts`
и завёл отдельный тест именно на это требование: `online → offline → online` через диспетчер должно
дать три сообщения.

**Результат — проверено.**
- `tsc` чисто. Тестов **71** (было 61), три прогона без флака.
- Главный тест — сквозной, через настоящий `NotificationDispatcher`: отправка упала → сообщения нет →
  следующий тик отправил → дальше два тика молчат. Плюс: повтор того же состояния не доставляется
  (5 тиков = 1 сообщение); смена и обратная смена доставляются; серверы независимы; упавшая отправка
  не запоминается; две одновременные доставки одного состояния дают одну отправку; `unknown`
  пропускается, остальные серверы при этом не задеты.
- Тесты доказанно ловят регрессию, три слома:
  1) запоминать **после** отправки → падает тест про одновременные доставки;
  2) убрать откат при отказе → падают тест про упавшую отправку и сквозной;
  3) публиковать `unknown` как `serverOnline` → падает тест про `unknown`.
  Плюс проверен сам тест про ловушку: подставил две обёртки вместо одной — падает.
- Живой smoke (разовый скрипт): реальный `Scheduler` с периодом 300 мс, фейковый Telegram, первая
  отправка падает, на 700 мс сервер 1 уходит в offline, а сервер 2 из `unknown` становится online.
  За 5 тиков — **3 сообщения**: «Server 1 is online» (повтор упавшего), «Server 1 is offline»,
  «Server 2 is online». Лишних нет, `unknown` молчал, пока не ответил.
- Приложение стартует как раньше.

**Побочно подтвердился п. 22 долга.** Правка контракта `CurrentStateSource` (добавился `getSnapshot`)
не была видна `tsc`, потому что тесты в `exclude`: фикстура в `StateSync.test.ts` осталась старой,
и это всплыло только на прогоне — 5 упавших тестов. Ровно тот сценарий, о котором мы говорили,
когда обсуждали смену интерфейса `ScheduledTask`.

**Известное следствие.** Память обёртки живёт в процессе, поэтому после рестарта первый тик
отправит статусы заново. Это не регресс: то же самое делает переход `unknown → online` на первом
опросе. Связано с п. 14 долга (`forceSync` пересоздаёт probes и даёт повторные «is online»).

**Статус:** ✅ сделано 2026-07-31. Не закоммичено. Тестов 71.

## Открытые темы для обсуждения

Не итерации — вопросы, которые надо продумать до того, как они станут итерациями.

### Тесты с БД и работа с SQL в целом

**Отложено 2026-07-30 до отдельного разговора.** Вернуться обязательно — сейчас `npm test` требует
живую MariaDB и падает без неё (`ER_GET_CONNECTION_TIMEOUT`).

Что уже выяснено, чтобы не выяснять заново:

- **Подменить MariaDB на SQLite в тестах нельзя.** Пакет `mariadb` — клиент одного протокола.
  `createPool` принимает connection string, но схема захардкожена регуляркой
  `/mariadb:\/\/.../` (`node_modules/mariadb/lib/config/connection-options.js:7`), выбора драйвера
  по схеме нет. Упоминаний sqlite/postgres в пакете нет вообще.
- **URL-выбор драйвера — свойство слоя абстракции, а не драйвера.** В JVM это JDBC (SPI + реестр),
  в Rails ActiveRecord, в Django ORM. В Node такого слоя нет ни в рантайме, ни в стандартной
  библиотеке — его приносит ORM/query builder. **Решение: ORM не вводим** (см. «Принятые решения»).
- **Диалект всё равно не переносится:** `bigint unsigned auto_increment`, `longtext collate
  utf8mb4_bin`, `timestamp ... on update current_timestamp()`, `TRUNCATE TABLE` — ничего из этого
  в SQLite нет. Схему пришлось бы держать под каждый диалект, то есть работать против цели
  итерации 6.
- **Тест против другой СУБД убирает именно то, что стоит проверять.** Живой пример:
  `ServerRepository.ts:33` делает `id: Number(row.id)`, потому что драйвер `mariadb` отдаёт `BIGINT`
  как `BigInt`. Драйвер SQLite вернул бы обычный `number`, и тест прошёл бы даже если это приведение
  убрать. То же касается `json_valid`-констрейнта, `ON UPDATE` на `updated_at` и ветки
  `typeof row.queryConfig === "string"`.
- **`node:sqlite` локально недоступен** (Node 20, `ERR_UNKNOWN_BUILTIN_MODULE`); появился в 22.5,
  экспериментальный. Понадобился бы `better-sqlite3` с нативной сборкой.

Направления, к которым вернуться:
1. **Разделить тест по уровням** (самое дешёвое и не требует ничего нового). Вся содержательная
   логика `ServerRepository` — в `parseQueryConfig`: разбор JSON, ветка «строка или объект»,
   проверка совпадения `query_type` с `type`, две разные ошибки. Ей БД не нужна — нужны
   фикстуры-строки. Вынести в чистую функцию, покрыть в `test:unit`; на SQL останется один
   интеграционный тест.
2. **Testcontainers** для этого одного теста: настоящая MariaDB, поднимается самим тестом.
   Цена — Docker и ~5–10 с на старт.
3. **`DB_URL` одной переменной вместо шести** — самостоятельная идея, к диалектам отношения
   не имеет. `createPool("mariadb://user:pass@host:3306/db")` работает уже сейчас; совпадает
   с тем, как креды выдают compose и облачные провайдеры.

Никаких `if (isTest)` в прод-коде при любом варианте: реализацию выбирает composition root
(итерация 2), прод-код зависит от интерфейса.

### `ServerProbe` таскается целым объектом там, где нужны отдельные факты

**Замечено 2026-07-30 (наблюдение zalex).** `ServerMonitor` почти везде оперирует probe как целым
объектом, а не запрашивает конкретные данные. Опасение: при изменении `ServerProbe` пойдут side effects
по всему монитору.

Конкретика, подтверждающая опасение. За **один** poll одного сервера `getSnapshot()` вызывается
**три раза**, и каждый раз собирается новый объект из шести полей вместе с полным `config`:
1. `pollProbe:51` — внутри `logger.debug(...)` через `getNextPollDelayMs(probe)`;
2. `pollProbe:52` — `probe.getSnapshot().config` ради одного `config.query`;
3. `Scheduler.getNextDelayMs` → `getNextPollDelayMs(probe)` — снова весь снапшот ради двух полей.

Дополнительно: `logger.debug` с шаблонной строкой вычисляет аргументы **до** проверки уровня, поэтому
в проде (уровень `info`) `getNextPollDelayMs()` и сборка снапшота выполняются на каждом poll каждого
сервера, а результат выбрасывается.

Что обсудить: probe как источник узких запросов (`getQueryConfig()`, `getPollHint()`) против нынешнего
«отдай всё, разберусь сам»; кто владеет решением о частоте опроса — монитор или probe; надо ли
`ServerSnapshot` вообще, если у него три разных потребителя с разными нуждами (`/time`, вид для
рендера, выбор задержки).

## Принятые решения

### DI-контейнер не вводим

**Решение принято 2026-07-30.** Ручная сборка графа в `main.ts` остаётся, DI-библиотека
(tsyringe / InversifyJS / Awilix / NestJS) не добавляется.

**Обоснование.** Проблема проекта не в том, что объекты создаются вручную, а в том, что они создаются
**в двух местах** и часть из них тянет зависимости из глобальных модулей. Контейнер это не лечит: он
автоматизирует сборку, а не централизует её. Масштаб — около 15 объектов, один singleton-scope, нет
per-request lifetimes, нет динамически загружаемых плагинов; `main.ts` — 101 строка. Цена контейнера
при этом реальна: декораторы + `reflect-metadata` конфликтуют с текущей связкой NodeNext ESM +
`verbatimModuleSyntax` + `isolatedModules` + `tsx`; ошибки сборки графа переезжают из компиляции
в рантайм; сам граф становится невидимым — вместо чтения одного файла нужно держать в голове правила
резолва.

**Что вместо.** Один composition root (итерация 2) + фабрики-модули по подсистемам, когда `main.ts`
начнёт разрастаться: `createMonitoring(deps)`, `createNotifications(deps)`. Граф остаётся видимым
и проверяется компилятором.

**Когда пересмотреть.** Сигналы, что контейнер начал бы окупаться: появились scoped-времена жизни
(например, объект на HTTP-запрос или на «сессию» опроса); объектов стало заметно больше пятидесяти;
нотифаеры/queriers грузятся динамически как плагины; в `main.ts` появились одинаковые цепочки сборки,
различающиеся одним параметром.

**Правило на будущее (не зависит от решения).** `container.resolve()` — если он когда-нибудь появится —
должен встречаться в проекте ровно один раз, в точке входа. Как только он вызывается внутри бизнес-класса,
это Service Locator, независимо от того, что библиотека называется «DI container».

### ORM не вводим

**Решение принято 2026-07-30 (решение zalex).** Ни Kysely, ни Drizzle, ни Knex, ни Prisma, ни
TypeORM. Запросы остаются рукописным SQL через `mariadb`.

**Контекст.** Вопрос возник из желания подменить MariaDB на SQLite в тестах через URL со схемой,
как во «взрослых» фреймворках. Такой выбор драйвера по схеме URL даёт только слой абстракции доступа
к данным, то есть ORM/query builder — драйвер `mariadb` этого не умеет и не может (подробности
и все выясненные факты — в «Открытых темах», раздел про тесты с БД).

**Почему отказ разумен.** Задача не требует того, что даёт ORM: одна таблица, один `SELECT`, нет
сложных запросов. При этом подмена диалекта в тестах активно вредит — тест на SQLite не проверяет
то поведение MariaDB, ради которого он написан. Быстрый прогон без БД достигается дешевле:
вынесением логики парсинга в чистую функцию.

**Что это НЕ отменяет.** Мигратор (итерация 6) всё равно нужен — его придётся сделать своими руками,
а не взять из ORM.

### `NotificationDispatcher` — диспетчер событий, а не транспорт

**Решение принято 2026-07-30.** Ответы на команды бота **не** идут через `NotificationDispatcher`. Транспортом
для Telegram является `TelegramSender` (владеет `Bot`, умеет отправить текст), и именно он —
то общее, что переиспользуется из разных мест. `NotificationDispatcher` знает только «событие типа X → вот эти
нотифаеры» и про чаты/адресатов не знает ничего.

**Почему не через `NotificationDispatcher`.** Уведомление и ответ на команду — разные по природе:
- направление: push, инициированный системой, в заранее известное место — против request-response,
  инициированного пользователем, с ответом туда, откуда пришёл запрос;
- адресация: у уведомления она фиксирована конфигом, у ответа берётся из контекста апдейта (`ctx`);
- семантика ошибок: `NotificationDispatcher` рассылает многим и глотает ошибки (`Promise.allSettled`), ответ уходит
  ровно одному и его неудача значима;
- если пропустить ответы через диспетчер, в словарь доменных событий придётся протащить транспортную
  адресацию («ответить в чат X на сообщение Y») — та самая протечка, которую мы убираем в итерациях 3 и 5.

**Адресация — параметр отправки, а не состояние конструктора.** Сейчас `TelegramSender` жёстко
держит один `chatId`, поэтому «отправить конкретному пользователю» невозможно. Ограничение здесь,
а не в `NotificationDispatcher`. Целевая форма: `send(chatId, text)`, а знание «куда именно» живёт в нотифаере
(это часть политики уведомлений — итерация 5).

**Слои.**
```
Транспорт   TelegramSender          умеет отправить текст в любой чат; единственный, кто знает grammy
Политика    *Handler                знает, ЧТО за событие и КУДА слать (канал / юзер / молчать ночью)
Диспетчер   NotificationDispatcher  знает только «тип события → нотифаеры»; про адресатов не знает
Команды     TelegramBot             через диспетчер не ходит, отвечает через ctx в контексте апдейта
```

### Telegram: два независимых переключателя

**Решение принято 2026-07-30.** Третий env-флаг не заводим.
- **Непустой `TELEGRAM_TOKEN`** = Telegram вообще доступен. Только при этом условии создаётся
  единственный на процесс экземпляр `Bot`, который отдаётся и в `TelegramBot` (команды), и в
  `TelegramSender` (отправка). Сейчас `Bot` создаётся дважды на одном токене
  (`Notifiers.ts:35` и `TelegramBot.ts:26`).
- **`TELEGRAM_NOTIFIER`** = слать ли уведомления о статусах серверов, и **только это**. Команды
  (`/time`, `/who`, `/id`) работают при любом его значении — флаг существует исключительно для
  отправки статусов серверов через `NotificationDispatcher`.

Отдельный флаг для команд (`TELEGRAM_COMMANDS`) не добавляем, пока не появится реальная нужда
выключать их при живом токене. Добавить его потом — одна строка в convict.

**Пустой токен: деградация, а не fail-fast (подтверждено 2026-07-30, решение zalex).**
Рассматривался вариант сделать `TELEGRAM_TOKEN` обязательным (convict `format` отвергает пустую
строку, приложение не стартует). Отклонён: **раз в конфиге есть `TELEGRAM_NOTIFIER`, значит работа
без Telegram уже предполагается дизайном** — было бы противоречиво разрешать выключать уведомления
флагом и одновременно требовать токен. Поэтому пустой токен = Telegram отключён целиком,
с предупреждением в логе, а не падение.

Следствие, которое надо помнить: у команд собственного флага нет, поэтому **непустой токен
и работает как их выключатель**. Пустой токен выключает и уведомления, и команды; `TELEGRAM_NOTIFIER`
выключает только уведомления. Это осознанно.

Что при этом было настоящим багом и починено в итерации 2: падало даже при `TELEGRAM_NOTIFIER=false`,
то есть флаг не работал; падало из конструктора grammy сообщением `Empty token!`, не называющим
ни переменную, ни сервис; `convict` считал такой конфиг валидным, потому что у `TELEGRAM_TOKEN`
стоит `default: ""` без `format`-ограничения.
